# 캐릭터·전환·던전·관문 통합 YOLO 연결

현재 기본 실행은 [역할별 모델 분리 구성](25-role-models-and-stable-context.md)입니다. 아래는 통합 모델 도입 당시의 기록입니다.

후속 수정: [실게임 진단 기반 인식 수정](24-live-recognition-fixes.md). 메뉴 내부의 레벨 줄 탐색과 검증된 창 우하단 로딩 보조 경로가 추가되어, 아래 초기 구현의 ‘탐지 실패 시 좌표 대체 없음’ 정책 중 로딩에 예외가 생겼습니다. 최신 전환/검증 기준은 후속 문서를 참고합니다.

2026-09-21. 다른 해상도 검증은 전체 기능 구현 이후로 미룹니다. 현재 해상도(3440×1440) 데이터만으로 먼저 모델을 학습하고 동작을 확인할 수 있도록 구성했습니다.

## 구현 범위와 현재 상태

전체 원본 화면을 한 번의 YOLO 호출로 분석하고, 탐지된 영역을 캐릭터 OCR·전환 판단·던전 OCR·관문 탐지·기록 저장에 연결했습니다. 새로운 경로에서는 캐릭터용 기존 고정 탐색 좌표나 메뉴 이미지 템플릿을 로드하지 않습니다. 기존 방식은 `legacy` 모드로 유지합니다.

2026-09-22 **7개 클래스 통합 모델을 학습하고 기본 모드를 `yolo`로 활성화했습니다.** 로컬 `models/ui-regions.pt`를 사용하며 앱 재시작 후 `UI 자동 탐지`가 표시됩니다. 다른 해상도·독립 양성 실게임 검증은 아직 수행하지 않았습니다.

## 탐지 클래스와 후속 처리

클래스 순서는 `config/ui-regions.json`과 학습 라벨에서 같아야 합니다.

| ID / 클래스 | 라벨 범위 | 후속 처리 |
| --- | --- | --- |
| 0 `game_menu` | 초상화와 캐릭터 목록을 포함한 메뉴 전체 | 현재 이름의 소속 영역과 일반 메뉴 복귀 확인 |
| 1 `current_name_line` | 초상화 아래 레벨 + 현재 이름 전체 줄 | 원본 OCR → 레벨 제거 → 2~12글자 검증 |
| 2 `switch_dialog` | 확인/취소를 묻는 캐릭터 변경 팝업 | 변경 의도 기억. 이때 기존 캐릭터 유지 |
| 3 `target_name_line` | 팝업 안 변경 대상 이름 줄 | 팝업 내부에 포함된 경우에만 대상 OCR |
| 4 `loading_indicator` | 오른쪽 아래 대기 문구·회전 아이콘을 함께 포함하는 영역 | 청록색 아이콘 + 대기 문구 확인 |
| 5 `dungeon_panel` | 제목·난이도·관문을 포함하는 던전 정보 패널 | 제목/난이도 상대 영역 계산 |
| 6 `gate_panel` | 관문 아이콘들이 있는 전체 줄 | 기존 관문 YOLO로 상태 분류 |

`loading_indicator`는 기존 450×170 로딩 영역과 같은 문구·아이콘 배치 및 여백 기준으로 라벨링해야 합니다. 탐지된 영역을 450×170으로 정규화한 뒤 내부 문구와 색상 근거를 확인합니다. 위치는 탐지 결과를 따르지만 내부 배치에 대한 가정은 남아 있습니다.

캐릭터 이름과 변경 대상은 직접 탐지한 원본 줄을 읽습니다. 이름 줄이 각각 메뉴와 팝업 안에 포함되지 않으면 읽지 않습니다. 로딩 중에는 현재 이름을 읽지 않아 이전 초상화의 재확정을 막습니다.

던전명·난이도는 패널 상대 위치를 사용합니다. `gate_panel`은 별도로 탐지하며 던전 패널 안에 들어 있어야 합니다. 관문 상태 모델이 반환하는 좌표는 기존 저장용 기준으로 정규화하므로 패널 이동이 관문 슬롯 변경으로 해석되지 않도록 합니다.

## 전환·누락 처리

- 팝업 표시만으로는 기록 중단이나 캐릭터 초기화를 하지 않습니다.
- 팝업 직후 검증된 로딩 표시를 관측하면 확인 대기로 전환합니다.
- 일반 메뉴로 복귀하면 취소로 처리합니다.
- 로딩 뒤 새로운 현재 이름을 연속 확인하면 새 캐릭터로 확정합니다.
- 동일 클래스의 겹친 후보는 IoU 0.4 기준으로 높은 신뢰도 후보를 남깁니다. 떨어진 후보가 여러 개면 모호한 상태로 처리합니다. 복수 팝업 후보는 ‘팝업 없음’으로 취급하지 않습니다.
- 탐지 누락 시 이전 좌표나 고정 좌표로 대신 OCR하지 않습니다. 이전에 확정한 캐릭터를 유지하는 기존 정책과 던전 정보 보류 정책은 그대로 적용합니다.
- 전체 화면 탐지 한 번만으로 모든 클래스 결과를 공유하므로 캐릭터와 던전이 서로 다른 프레임에 근거해 판단하지 않습니다.

## 설정 우선순위

1. `config/ui-regions.json`의 `mode=yolo`: 통합 경로. `models/ui-regions.pt` 필요.
2. 통합 설정이 `legacy`이고 `config/dungeon-panel.json`이 `yolo`: 앞 단계의 던전 패널 전용 경로.
3. 두 설정 모두 `legacy`: 기존 인식 경로.

통합 모델 활성화 시 기존 3클래스 캐릭터 모델을 잘못 지정하면 클래스 검사에서 거부합니다. 배포 도구도 활성화된 통합 모델을 포함하도록 연결했습니다. 설정을 바꾼 뒤 앱을 재시작합니다.

## 현재 해상도 학습 절차

원본 메뉴 화면, 변경 확인 팝업, 취소 복귀, 확인 후 로딩, 일반 필드, 던전별 관문 화면을 모읍니다. 같은 해상도라도 train과 val은 서로 다른 플레이 세션으로 분리합니다. 통합 대상 UI가 하나도 없는 화면은 `boxes: []`로 포함합니다. 던전 밖이라도 메뉴가 있다면 음성 화면이 아니라 메뉴 양성 라벨을 작성해야 합니다.

라벨 JSON의 `classes`는 설정의 7개 클래스 순서를 그대로 사용합니다. 각 이미지에는 상대 파일 경로 `path`, `sessionId`, `split`(`train` 또는 `val`), `boxes`가 필요합니다. 각 상자는 다음처럼 작성합니다. 아래 좌표는 형식 예시이며 원본에 맞춰 표시해야 합니다.

```json
{"class": "current_name_line", "xyxy": [760, 897, 1310, 925]}
```

```powershell
.venv-win/Scripts/python.exe tools/train_dungeon_panel.py prepare data/annotations/ui-regions.json --classes-config config/ui-regions.json --output outputs/ui-regions-dataset
.venv-win/Scripts/python.exe tools/train_dungeon_panel.py train outputs/ui-regions-dataset/dataset.yaml --weights models/character-yolo26n-first.pt --name ui-regions --epochs 80 --device cpu
```

기존 YOLO 가중치는 학습 초기값으로만 사용합니다. 데이터 준비 시 모든 클래스의 train/val 포함 여부, 원본 크기 내 좌표, 세션 분리와 중복 파일을 검사합니다. 모델은 자동으로 활성화하지 않습니다.

학습 후 현재 해상도의 별도 이미지에서 위치와 OCR을 함께 확인합니다.

```powershell
.venv-win/Scripts/python.exe tools/inspect_ui_regions.py path/to/game.png --weights outputs/training/ui-regions/weights/best.pt --output outputs/ui-check
```

`regions.png`는 원본 위 탐지 상자이며 `observation.json`에는 캐릭터·대상·로딩·던전·관문 결과가 들어갑니다. 정지 이미지 검사와 시간 순서에 따른 변경/취소 검증은 구분해야 합니다.

현재 해상도에서 학습 모델 동작 확인 → 전체 기능 연결 확인 → 다른 해상도·화면 비율·UI 배율 검증 순서로 진행합니다.

진단 보강 후 앱을 재시작하면 `%LOCALAPPDATA%/BeatricePC/recognition-diagnostics`에 최근 게임 화면 JPG와 같은 프레임의 탐지·OCR·관문·상태 JSON을 최대 180쌍 보관합니다. 1초 간격 및 감지된 캐릭터 상태 변화 시 저장하며 오래된 슬롯은 순환 덮어씁니다. 게임 창 캡처만 저장하며 업로드하지 않습니다. 실패 직후 정지하면 분석 자료가 보존됩니다. 짧은 팝업이 추론 프레임 사이에 지나가면 여전히 포착하지 못할 수 있으며, 이 경우 관측 간격도 함께 조사해야 합니다.
