# YOLO·OCR 인식 구조와 운영 기준

작성일: 2026-09-21. 현재 Windows 실시간 앱 코드와 이번 개발 과정의 검증 결과를 기준으로 작성했습니다. 과거 단계별 문서와 구현이 다르면 이 문서와 현재 코드를 먼저 확인합니다.

## 1. 역할과 전체 흐름

YOLO는 화면의 영역과 관문 아이콘 상태를 찾고, OCR은 그 영역의 문자를 읽습니다. 캐릭터 이름이나 던전 이름을 YOLO의 개별 클래스로 학습하는 구조가 아닙니다. 새 이름을 인식하기 위해 이름 목록에 등록하거나 이름별로 재학습할 필요는 없습니다. 다만 새로운 글꼴·배치·배경에서의 정확도는 별도 검증이 필요합니다.

| 구성 | 현재 역할 | 모델 / 구현 |
| --- | --- | --- |
| 관문 YOLO | 진행중·완료·진행 전 아이콘 탐지 | `models/gates-yolo26n-first.pt` |
| 캐릭터 YOLO | 현재 이름·변경 대상 이름·변경 확인 팝업 영역 탐지 | `models/character-yolo26n-first.pt` |
| 한국어 OCR | 캐릭터명, 던전명, 난이도, 팝업 제목, 로딩 문구 읽기 | PaddleOCR `korean_PP-OCRv5_mobile_rec` |
| 시간 안정화 | 반복 관측을 통해 이름과 이벤트 확정 | `CharacterTracker`, `DungeonTracker`, `GateTracker` |
| 저장 연결 | 확정 캐릭터 기록 및 미확정 기록 보존 | `LiveCoordinator`, `DeferredRecordingSession` |

```text
게임 창 클라이언트 영역 캡처
  ├─ 중앙 기준 보정 → 캐릭터 YOLO / 메뉴 판별 → 이름 OCR
  ├─ 원본 창 오른쪽 아래 → 로딩 아이콘 + 대기 문구 확인
  └─ 좌상단 기준 보정 → 관문 YOLO → 던전명·난이도 OCR
                         ↓
             프레임 간 안정화와 캐릭터 전환 판단
                         ↓
                 화면 표시 / SQLite 저장
```

실시간 앱은 CPU에서 실행합니다. 던전 OCR과 캐릭터 OCR은 하나의 Paddle 인식기 인스턴스를 공유합니다. 루프는 최소 0.5초 간격을 목표로 하지만 분석에 더 오래 걸리면 실제 관측 간격도 늘어납니다. ‘3회 확인’이 항상 1.5초를 의미하지는 않습니다.

## 2. 캡처와 좌표 기준

기준 화면 크기는 3440×1440이며, 좌표는 `(왼쪽, 위, 오른쪽, 아래)` 순서입니다. 화면 높이와 사용자 UI 배율로 보정합니다.

현재 좌표 설정과 테스트는 기준 해상도(3440×1440)를 중심으로 진행했습니다. 좌표 보정 코드가 있어도 다른 해상도에서의 정상 동작이 검증된 것은 아닙니다. 다른 해상도·화면 비율·UI 배율에서 추가 테스트가 필요합니다. 대안으로는 고정 좌표에 대한 의존을 줄이고, YOLO로 필요한 UI 영역의 위치를 직접 탐지한 뒤 해당 영역에 OCR을 적용하도록 확장할 수 있습니다. 현재 YOLO도 미리 정한 탐색 영역 안에서 동작하므로, 해상도와 관계없이 위치를 찾는 구조는 아직 구현·검증되지 않았습니다.

| 대상 | 좌표 / 기준 | 비고 |
| --- | --- | --- |
| 관문 탐지 | `(32, 112, 352, 224)` | 좌상단 기준 |
| 캐릭터 탐지용 초상화 영역 | `(900, 850, 1140, 960)` | 중앙 기준 |
| 캐릭터 탐지용 팝업 영역 | `(1440, 560, 2000, 880)` | 중앙 기준 |
| 현재 이름 OCR 탐색 줄 | `(760, 897, 1310, 925)` | `Lv.숫자`까지 포함 |
| 변경 대상 이름 OCR 탐색 줄 | `(1552, 655, 1888, 688)` | 이름 길이를 고려한 폭 |
| 일반 메뉴 비교 영역 | `(1160, 415, 2040, 840)` | 메뉴 참조 이미지와 비교 |
| 팝업 제목 보조 OCR | `(1460, 588, 1980, 642)` | ‘다른 캐릭터 바로 접속’ 확인 |
| 던전명 OCR 탐색 줄 | `(25, 63, 800, 87)` | 실시간 입력의 최대 탐색 폭 |
| 난이도 OCR | `(140, 98, 240, 120)` | 좌상단 기준 |
| 로딩 표시 | 원본 창 오른쪽 아래 450×170 상당 영역 | 높이/UI 배율 반영 후 450×170으로 정규화 |

탐지된 캐릭터 이름 상자가 짧더라도 OCR 줄의 폭을 그 상자에 맞춰 줄이지 않습니다. 탐지 상자의 세로 위치와 더 넓은 좌우 범위는 반영합니다.

`config/dungeon-ocr.json`의 던전명 오른쪽 좌표는 과거 값 355가 남아 있지만, 현재 `analyze_panel()`이 입력 패널 너비에 맞춰 최대 800으로 확장합니다. 기존 400×240 패널도 읽을 수 있으나 패널 밖으로 잘린 문자는 복원할 수 없습니다. 신규 영상 분석 패널은 800×240으로 보존합니다.

게임 창이 비활성화되거나 최소화되면 캡처를 기다립니다. 이것만으로 캐릭터 이름을 초기화하지 않습니다. UI 배치가 기준과 크게 다르면 배율 보정만으로 해결되지 않을 수 있습니다.

## 3. 캐릭터 이름 인식

1. YOLO로 이름 영역을 찾습니다. 일반 메뉴가 참조 이미지와 0.90 이상 일치하면 탐지 실패 여부와 관계없이 현재 이름 줄을 읽습니다.
2. 넓게 잡은 줄에서 밝은 흰색·노란색 글자 군집을 찾아 배경 여백을 제거합니다.
3. 회색조 원본과 3배 확대 이미지에서 각각 OCR을 실행합니다.
4. 현재 이름 줄에서는 맨 앞의 `Lv.숫자`만 제거합니다. 변경 대상 이름에는 이 제거를 적용하지 않습니다.
5. 두 전처리 결과의 이름이 같고 최소 신뢰도가 0.65 이상일 때 유효한 관측으로 사용합니다.
6. 같은 이름이 3회 연속 관측되면 현재 캐릭터로 확정합니다. 확정 전 읽힌 이름은 ‘확인 중’으로 표시할 수 있습니다.

이름은 NFC 정규화 후 2~12글자이며 모든 글자가 `isalnum()` 조건을 만족해야 합니다. 이름 내부의 영문·숫자는 보존합니다. 레벨 접두사는 현재 1~2자리 숫자를 처리합니다. 알려진 이름과 비슷하다는 이유로 문자열을 바꾸지 않습니다.

실시간 `CharacterTracker`의 관측 간격 한도는 5초입니다. 이를 넘으면 연속 확인 횟수를 초기화하지만 이미 확정한 이름 자체를 지우지는 않습니다.

## 4. 캐릭터 변경과 취소

입력 클릭이나 키보드를 감시하지 않습니다. 화면의 순서를 이용해 전환 시작을 판단합니다.

| 관측 | 캐릭터 상태 / 저장 처리 |
| --- | --- |
| 변경 확인 팝업만 표시 | 기존 캐릭터 유지, 대상 이름과 최근 팝업 시각만 기억 |
| 로딩 없이 일반 메뉴로 복귀 | 취소로 처리하고 임시 변경 대상을 해제 |
| 최근 팝업 이후 로딩 아이콘과 대기 문구 표시 | `suspend` 발생, 캐릭터 확인 대기로 전환, 기존 저장 구간 분리 |
| 로딩 표시가 계속 보임 | 반복 `suspend` 없이 대기 유지, 남아 있는 초상화로 확정하지 않음 |
| 로딩 종료 후 새로운 현재 이름 3회 확인 | 새 캐릭터 확정 및 저장 연결 |
| 팝업 이력 없는 로딩·검은 화면·맵 이동 | 기존 캐릭터 유지 |
| 팝업/로딩을 놓쳤지만 다른 현재 이름 관측 | 기존 이름으로 계속 기록하지 않고 새 이름을 재확인 |

팝업 판별은 YOLO와 제목 OCR을 함께 사용합니다. 제목 OCR은 신뢰도 0.85 이상이며 공백을 제거한 문구에 ‘다른캐릭터바로접속’이 포함되는지 확인합니다.

로딩 판별은 오른쪽 아래 청록색 아이콘 후보와 ‘잠시만 기다려주세요’ 문구를 모두 요구합니다. 문구 신뢰도 기준은 0.85입니다. 아이콘은 회전 모양 하나를 템플릿으로 고정하지 않고 해당 영역의 청록색 픽셀을 확인합니다. 따라서 아이콘 단독 검출은 전환 근거가 아닙니다.

최근 팝업의 유효 시간은 `max(3초, max_gap × 2)`이며 실시간 앱에서는 10초입니다. 팝업을 계속 보면 기한이 갱신됩니다. 일반 메뉴 복귀 또는 기한 만료 시 이력을 해제해 나중의 일반 로딩과 연결하지 않습니다.

전환 시작 후 이전 이름은 재확정하지 않습니다. 전환이 실패해 이전 캐릭터로 복귀하는 경로는 별도 복구 판단이 아직 없으므로 대기가 유지될 수 있습니다. 짧은 팝업·로딩이 분석 프레임 사이에 지나가면 전환 시작을 놓칠 수 있습니다.

## 5. 던전 이름과 난이도

실시간에서는 같은 위치에 글자가 있다는 이유만으로 던전 정보를 표시하지 않습니다. 다음 근거를 함께 확인합니다.

- 기준 영역 안에서 신뢰도 0.65 이상인 관문 아이콘이 1~8개 존재해야 합니다.
- 관문 상태는 진행중·완료·진행 전 중 하나여야 합니다.
- OCR로 읽은 난이도가 노말·하드·헬·익스트림·싱글 모드 중 하나여야 합니다.

관문 YOLO의 실시간 설정은 `imgsz=320`, `conf=0.65`, `iou=0.5`, `agnostic_nms=True`입니다. 동일 위치를 서로 다른 상태로 중복 탐지하는 경우를 줄입니다. 낮은 신뢰도 후보 하나가 유효한 던전 전체를 무효화하지 않도록 HUD 확인에서 해당 후보를 제외합니다.

던전명은 최대 800 너비의 패널에서 실제 글자 줄을 찾습니다. 단어 사이 공백도 같은 줄로 연결하도록 글자 군집 연결 폭을 24픽셀로 설정합니다. 이후 회색조·3배 확대·반전의 세 가지 결과를 비교합니다.

OCR 합의는 다음과 같습니다.

- 신뢰도 0.5 이상인 결과를 모읍니다.
- 공백과 일부 UI 구두점(`, : [ ]`) 차이를 정규화해 같은 문자열인지 비교합니다.
- 한 문자열에 2회 이상 합의하고 최고 신뢰도가 0.65 이상이어야 합니다. 다른 문자열 후보가 함께 존재하면 보류합니다.
- 표시 문자열은 합의한 결과 중 신뢰도가 가장 높은 원문을 사용합니다. 비슷한 다른 글자로 보정하지 않습니다.

`supportedDungeonNames`는 참고 목록이며 인식 허용 목록이 아닙니다. 반면 `supportedDifficulties`는 실시간 던전 화면 판별에 사용하는 제한 목록입니다. 새로운 난이도 종류는 이 설정에 추가해야 합니다.

`DungeonTracker`는 이름·난이도를 각각 3회 연속 확인합니다. 첫 유효 관측은 ‘확인 중’으로 표시하고, 실패하면 해당 필드의 이전 값을 재사용하지 않습니다. 두 필드가 모두 확정되어야 `ocr_verified`가 됩니다. 실시간 관측 간격 한도는 5초입니다.

`analyze_panel()`은 저장된 패널의 OCR 자체를 검사하는 함수로, 관문 HUD 검사를 수행하지 않습니다. 실시간 `analyze(frame, gate_boxes=...)`와 구분해야 합니다.

## 6. 표시와 기록 확정의 차이

OCR 관측, 현재 캐릭터 확정, 완료 이벤트 저장은 별도 단계입니다. 글자가 한 번 읽혔다고 즉시 완료 기록을 생성하지 않습니다.

`LiveCoordinator`는 확정된 던전명·난이도·관문 수가 3회 연속 같을 때 저장 구간을 준비합니다. 관문 진행→완료 판단은 `GateTracker`가 담당합니다. 캐릭터가 미확정이면 기록은 임시 보존하고 이후 이름 확인으로 연결합니다. 캐릭터 변경이 확인되면 이전 구간과 새 구간을 분리합니다.

현재 실시간 저장은 테스트 정책(`is_test=True`)입니다. 같은 캐릭터·던전·난이도·관문은 전체 기록 삭제 전까지 한 번 저장하는 정책이므로 주간 초기화나 실제 서비스 중복 정책과 동일하지 않습니다.

## 7. 발견한 문제와 수정 근거

| 문제 | 원인 | 현재 처리 |
| --- | --- | --- |
| 등록한 던전명만 인식 | 이름 목록을 OCR·안정화·저장 검증에 사용 | 이름 목록 제한 제거, 화면 구조로 던전 판별 |
| 긴 캐릭터명 잘림 | 3글자 학습 상자와 고정 이름 시작점 의존 | 레벨을 포함한 넓은 줄에서 읽고 레벨만 제거 |
| 이름 인식이 전부 실패 | 넓어진 영역의 배경까지 OCR, 불필요한 기호와 낮은 신뢰도 발생 | 글자 군집을 먼저 추출하고 PaddleOCR 사용 |
| 던전 밖 텍스트 표시 | 화면 맥락 없이 좌표만 보고 OCR | 관문 HUD와 난이도 동시 확인 |
| 제목 일부 단어만 읽음 | 공백을 서로 다른 글자 군집의 경계로 처리 | 단어 사이 연결 폭 확대 |
| 제목을 읽었지만 보류 | 전처리별 띄어쓰기 차이를 다른 문자열로 판단 | 공백·UI 구두점 정규화 후 합의 |
| 팝업만 열어도 캐릭터 대기 | 팝업 표시 자체를 전환 시작으로 처리 | 최근 팝업 + 로딩 표시의 순서로 판단 |
| 맵 이동도 캐릭터 변경으로 오인 | 검은 화면을 전환 근거로 사용 | 검은 화면·캡처 중단 단독 초기화 제거 |

| 사용자 던전 스크린샷 | `2막: 부유하는 악몽의 진혼곡 / 싱글 모드` 인식 | 해당 이미지에서 실물 OCR 확인 |
| 확인 후 로딩 스크린샷 | 아이콘 + 대기 문구 감지, 문구 신뢰도 약 0.990 | 한 장의 실제 로딩 표시 확인 |
| 사용자 실게임 확인 | 텍스트 인식 및 마지막 변경 적용 후 확인 응답 | 모든 해상도·전환 경로의 포괄 검증은 아님 |

프로젝트 루트의 PowerShell에서 실행합니다.

```powershell
.venv-win/Scripts/python.exe -m unittest discover -s tests -v
.venv-win/Scripts/python.exe tools/diagnose_character_lines.py
```

캐릭터 이미지 검사 보고서는 `outputs/character-diagnosis.json`에 저장됩니다. 로컬 던전 샘플 검증 결과는 `outputs/dungeon-sample-check.json`에 있습니다. `outputs` 파일 및 원본 샘플은 다른 체크아웃에 없을 수 있습니다.

## 9. 진단과 유지보수

`Run-Beatrice.cmd`로 시작한 앱의 기본 데이터 위치는 `%LOCALAPPDATA%/BeatricePC`입니다.

| 파일 | 확인할 내용 |
| --- | --- |
| `character-diagnostic.json` | 약 2초마다 최신 관측으로 덮어씀. 화면 크기, UI 배율, 탐지 상자, 메뉴 점수, OCR 원문, 로딩 판단 |
| `runtime.log` | 모델 라이브러리 출력 |
| `errors.log` | 작업자 실행 오류 |
| `startup-error.log` | 앱 시작 오류 |
| `records.sqlite3` | 완료 및 임시 기록 |

인식 실패 시 영역 탐지 여부 → OCR 원문 → 접두사/길이 검증 → 신뢰도 → 전처리 합의 → 연속 관측 순서로 확인합니다. 로딩 문제는 `ocr.loading.iconVisible`, `ocr.loading.raw`, `switchLoading`을 확인합니다. 진단 파일은 최신 관측 하나만 담으므로 지나간 전환 전체를 재현하는 로그는 아닙니다.

동작 변경 후에는 모의 OCR을 사용하는 단위 테스트뿐 아니라 실제 이미지를 반드시 비교합니다. 새로운 해상도·UI 배율·글꼴·긴 이름·취소·빠른 전환·일반 맵 이동은 추가 실게임 검증 대상입니다. 화면 OCR 방식이므로 모든 이름의 무오독을 보장하지 않습니다.
