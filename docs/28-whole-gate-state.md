# 전체 관문 현재 상태 저장과 완료 지연 보완

2026-09-23. 실시간 앱의 최신 정책입니다. 이전 문서의 최초 완료 관측 무시 정책을 대체합니다.

## 저장 정책

- 전체 N개 관문의 순서·개수·위치·상태를 연속 관측으로 검증한 뒤 최초 상태를 저장합니다. 진행 전 / 진행 중 / 완료 모두 저장하며, 처음부터 완료여도 저장합니다.
- 전체 상태 배열의 변경을 확정하면 하나의 SQLite 트랜잭션으로 갱신합니다. 중간 오류가 생기면 모든 변경을 취소합니다. 관문 일부가 누락된 프레임으로 기존 행을 삭제하지 않습니다.
- 초기화 전까지 `캐릭터 + 던전 + 관문 번호`별 현재 상태 행 하나만 유지합니다. 난이도는 기록 속성이며 중복 방지 키에 포함하지 않습니다. 새 완료 이력을 계속 추가하지 않습니다.
- 완료로 저장된 행은 이후 낮은 상태를 읽거나 재입장·앱 재시작해도 변경하지 않습니다. 다른 미완료 관문은 검증된 새 상태로 갱신할 수 있습니다.
- N관문 완료가 확정되면 앞선 1..N-1관문 중 완료가 아닌 상태를 완료로 보완합니다. 특정 1·2관문에 한정하지 않습니다. 보완 근거를 별도로 표시하고 실제 과거 완료 시각을 만들어 넣지 않습니다.
- 변경 확인 시각은 인식이 확정된 관측 시각입니다. 게임 서버의 실제 완료 시각을 뜻하지 않습니다.
- 수동 `기록 전체 삭제`가 현재 초기화 조건입니다. 자동 초기화 정책과 초당 3회 분석은 이번에 적용하지 않았습니다.

전체 배열은 현재 화면에서 관측되는 아이콘을 기준으로 검증합니다. 저장된 관문 수가 있으면 그 수와도 일치해야 합니다. 최초 진입 시 같은 아이콘이 지속적으로 누락되는 경우까지 검증됐다는 뜻은 아니며, 실제 여러 관문 구성의 추가 시험이 필요합니다.

## 구현과 기존 기록

`StateSession`이 실시간 관측을 처리하고 `gate_states` 테이블에 현재 상태를 저장합니다. UI는 모든 상태와 확인 근거를 표시합니다. 캐릭터 미확정 구간은 별도 소유자로 보류하고 해당 구간의 이름 확정 후 옮깁니다. 기존 전체 배열보다 짧은 보류 배열은 기존 기록을 덮어쓰지 않습니다.

DB 버전 3으로 전환할 때 던전명이 있는 기존 완료 이벤트를 완료 상태로 가져옵니다. 기존 이벤트 테이블은 호환성을 위해 보존하지만 새 실시간 기록을 누적하지는 않습니다. 던전명 없는 옛 이벤트와 옛 미확정 이벤트는 원본 테이블에 남으며 새 상태 표에는 자동 표시하지 않습니다. 동기화는 이번 작업 범위가 아닙니다.

## 인식과 지연 보완

- 관문 상태 YOLO를 두 관문 모두 완료된 실제 화면과 작은 crop 위치 변화로 보완 학습했습니다. 기존 진행 중·진행 전·일반 화면 예제를 함께 포함했습니다. 신뢰도 기준 0.65는 유지합니다.
- 예상 관문보다 적게 검출되면 수평 ±2픽셀 crop을 각각 한 번 검사합니다. 두 결과가 전체 개수·상태·위치에 동의할 때만 보완합니다.
- 관문 배열 검증 전에 중복 적용되던 3회 대기를 제거했습니다. GateTracker의 연속 3회 검증은 유지합니다.
- 두 영역 모두 사라진 경우 이전 위치 재사용은 최대 3초입니다. 현재 던전 패널이 같은 위치로 새로 탐지되고, 현재 제목·모드·전체 관문도 확인되면 위치 검증 시점을 갱신합니다. 검은 화면이나 읽을 수 없는 화면은 이 시간을 연장하지 않습니다.
- UI 부재가 1초 이상 이어진 뒤 15초 안에 다른 던전명·모드가 연속 3회 확인되면 전환을 확정할 수 있습니다. 검은 화면만으로 던전을 바꾸지 않습니다. 그 외 일시적 다른 값은 기존 10초 유지 규칙을 적용합니다.

관문 학습 실행: `gate-state-refresh`, 이전 관문 모델에서 40 epoch, freeze 10, AdamW lr 0.0005, imgsz 320, seed 42. 학습 메타데이터는 `data/annotations/gate-state-refresh.json`입니다. 9개 원본 crop에서 위치·폭 변형 54개를 구성했습니다. 학습/검증 원본이 같은 재현 검사이므로 독립 정확도 수치로 해석하지 않습니다. 기존 관문 학습 원본 전체는 이 작업 환경에 없으므로 이전 가중치에서 이어 학습했습니다.

## 검증

- 자동 테스트 113개 통과: 임의 N관문 보완, 완료 고정, 재시작·모드 변경, 누락된 배열 차단, 원자적 저장, 변경 없는 반복 관측의 무쓰기, crop 합의, UI 전환 등을 확인했습니다. 별도 임시 DB를 사용하는 Qt 검사에서 세 가지 상태가 표에 표시되는 것도 확인했습니다.
- 실제 DB 스냅샷 복사본에서 기존 완료 2개 유지, 버전 3 변환, 재열기, 낮은 상태로 변경 차단, 수동 초기화를 확인했습니다. 사용자 실행 DB를 직접 수정하지 않았습니다.
- 기존 화면 55개 검사 통과. 별도 기본 회귀 검사에서 영역 32/32, 추가 오탐 0, 기능 11개, 캐릭터 전환 6개, 일반 화면 4개를 통과했습니다.
- 이전 1관문 완료 기록 180프레임도 재생했습니다. 65프레임에 `[진행 중, 진행 전]`을 최초 저장하고, 완료가 보인 216프레임에서 두 프레임 뒤인 218프레임에 `[완료, 진행 중]`으로 함께 갱신했습니다. 결과는 `outputs/gate-state-refresh/first-replay.json`에 있습니다.
- 지연이 발생했던 180프레임 재생에서 최초 `[완료, 진행 중]`을 저장한 뒤 `[완료, 완료]`로 갱신했습니다. 2관문 완료가 보인 16:00:10.875 KST에서 새 확정 시점 16:00:27.264까지 약 16.4초입니다. 기존 실시간 확정은 16:00:41.028(약 30.2초), 실제 DB 저장은 41.880(약 31초)이었습니다.
- 완료 연출 중 UI가 사라졌다가 16:00:23.604에 다시 보입니다. 이 시점부터는 약 3.7초에 확정됩니다. 화면이 안 보이는 동안 새 상태를 추정 저장하지 않으므로 이 재생의 지연이 전부 제거되지는 않았습니다.

재생은 저장된 JPEG와 당시 관측 시각을 사용하고 확정된 캐릭터 이름을 복원했습니다. 학습 세션과 인접 프레임이 포함되어 있으며, 실게임에서 새로 측정한 응답 시간이나 이름 OCR 검증이 아닙니다. 3440×1440 외 해상도는 아직 검증하지 않았습니다.

결과: `outputs/gate-state-refresh/final-replay.json`, `final-replay.summary.json`, `audit-result.json`, `bootstrap-check/report.json`, `outputs/state-tests-final.log`. 활성 모델 경로는 기존 `models/gates-yolo26n-first.pt`를 유지하며, 활성화 정보는 `config/gate-state-model.json`에 기록합니다. 이전 가중치는 `outputs/gate-state-refresh/before.pt`에 보관합니다.

## 후속 실게임 확인과 오류 로그

2026-09-23 사용자 테스트에서 정상 동작하는 것으로 확인했습니다. 모든 던전·해상도와 전환 경로가 검증됐다는 의미는 아닙니다.

직전 저장 실패 신고를 조사했을 때 앱은 수정 완료 전인 21:10부터 실행 중이었고, 실제 DB는 버전 2이며 `gate_states` 테이블도 없었습니다. 코드 교체 후 분석 정지·시작만으로는 이미 불러온 모듈이 갱신되지 않습니다. 완전 종료 후 프로젝트의 `Run-Beatrice.cmd`로 다시 실행해야 합니다.

당시 최근 180프레임은 `5단계 [하드] 맹렬한 업화` 화면으로 던전·관문 영역이 모두 미탐지였습니다. 앞서 검증한 관문 아이콘 UI와 구성이 달라 해당 화면 지원은 별도 검증이 필요합니다. 앞선 던전 테스트 장면은 순환 진단에서 이미 덮어써졌으므로 같은 원인으로 단정하지 않았습니다.

로그 위치는 `%LOCALAPPDATA%/BeatricePC/`입니다.

- `errors.log`: 분석 작업 중 예외. 점검 당시 마지막 파일 갱신은 23:38:16이며 마지막 예외는 `게임 창이 종료됐습니다. 다시 선택해주세요.`였습니다. 캡처 대상 창이 더 이상 유효하지 않을 때 발생합니다. 인식·DB 저장 관련 새 예외는 발견하지 못했습니다.
- `runtime.log`: 라이브러리 출력과 경고. `ccache` 미설치와 CPU 환경의 `pin_memory` 경고가 있었으며 저장 실패 예외는 아니었습니다.
- `startup-error.log`: 앱 시작 실패 시 생성합니다. 이번 점검 시 파일이 없었습니다.
- `recognition-diagnostics/`: 최근 최대 180개 화면과 인식·상태 결과를 순환 보관합니다. 인식 누락은 예외 로그가 없어도 발생할 수 있으므로 함께 확인해야 합니다.

옛 한글 인코딩 오류는 누적 로그에 남아 있었으며 이번 실행의 새 오류가 아닙니다. 현재 예외별 시각을 별도 기록하지 않으므로 파일 갱신 시각만으로 모든 과거 오류 시점을 판별할 수는 없습니다. 오류 로그와 사용자 DB는 삭제하지 않았습니다.
