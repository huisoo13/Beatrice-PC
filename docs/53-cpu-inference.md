# CPU 추론 최적화

2026-10-06. OCR 일괄 제출 다음 단계로 사용자의 승인을 받고 CPU 추론만 최적화했다. OBS 프레임 대기 처리는 아직 변경하지 않았다.

## 적용한 설정

`config/cpu-inference.json`에서 YOLO 4스레드, OCR 4스레드, OCR oneDNN(MKLDNN) 가속을 사용한다. 사용 가능한 논리 CPU가 설정값보다 적으면 그 수로 제한한다. 변경은 앱 프로세스 내부에만 적용된다.

- YOLO 첫 CPU 추론 준비가 라이브러리 기본 스레드 수로 되돌리는 것을 확인했다. 추론 전후에 설정을 적용해 초기화 이후에도 4스레드를 유지한다.
- OCR 모델을 oneDNN CPU 가속으로 준비한다. 가속 초기화 또는 추론이 실패하면 로그에 이유를 남기고 기존 비가속 CPU 모델로 재시도한다. 일부 결과가 나온 뒤 실패해도 해당 입력 전체를 다시 처리하며 결과를 섞지 않는다. 비가속 방식도 실패하면 오류를 전달한다.
- 모델 파일·클래스·입력 해상도·OCR 전처리·신뢰도 기준·확정 조건·관측 간격은 변경하지 않았다. OCR의 내부 `batch_size=1`도 유지한다.

## 설정 비교

현재 PC의 같은 보존 프레임으로 모델 준비 이후 반복 측정했다.

| 비교 | 중앙값 |
| --- | ---: |
| YOLO 8스레드 | 125.3ms |
| YOLO 4스레드 | 120.2ms |
| YOLO 2스레드 | 189.5ms |
| YOLO 1스레드 | 297.1ms |
| OCR 4스레드·비가속 | 548.4ms |
| OCR 2스레드·비가속 | 566.8ms |
| OCR 1스레드·비가속 | 586.2ms |
| OCR 4스레드·oneDNN | 118.1ms |

YOLO 비교는 10장, OCR 비교는 글자 영역이 있는 7장이다. YOLO 탐지 상태와 정수 픽셀 좌표는 10/10 같았고, OCR 최종 텍스트·판정은 7/7 같았다. 개선의 대부분은 OCR CPU 가속에서 나왔다.

## 전체 분석 경로 재생

게임 진단 화면 10장에 종탑·캐릭터 선택 보존 화면 10장을 더해 고정된 20장으로 비교했다. 현재 YOLO 모델로 다시 탐지하고 캐릭터·던전·완료 분석을 실행했다. 각 화면에서 준비 실행 1회 뒤 3회 측정한 중앙값을 사용했다. 캡처·SQLite·진단 이미지 저장은 포함하지 않는다. 실제 앱의 표시 시간이나 게임 성능을 직접 측정한 값은 아니다.

| 화면 분류 | 기존: YOLO 8스레드·OCR 비가속 | 적용: YOLO 4스레드·OCR 가속 |
| --- | ---: | ---: |
| 전체 20장 중앙값 | 301.3ms | 237.1ms |
| 던전 진단 4장 중앙값 | 875.3ms | 431.4ms |
| 캐릭터 진단 3장 중앙값 | 248.4ms | 98.1ms |
| 기타 진단 3장 중앙값 | 233.3ms | 236.9ms |
| 추가 재생 10장 중앙값 | 337.3ms | 236.9ms |
| 20장 중 최대 | 885.8ms | 449.0ms |

탐지 위치·텍스트·판정 결과 **20/20 동일**. 신뢰도 수치의 최대 차이는 약 `5.36e-7`이었다. 기타 화면에서는 소폭 느려졌으므로 모든 장면이 빨라졌다고 해석하지 않는다. 이 자료는 동일 보존 화면 비교이며 독립 정확도 검증이 아니다.

측정·비교 결과는 `outputs/cpu-inference/`의 `pipeline-baseline.json`, `pipeline-optimized.json`, `comparison.json`에 저장했다. 사용 패키지는 Torch 2.8.0, Ultralytics 8.4.152, PaddlePaddle 3.3.1, PaddleOCR 3.7.0, PaddleX 3.7.2였다.

재현 도구: `python -m tools.benchmark_cpu_inference pipeline --threads 8 --output outputs/cpu-inference/pipeline-baseline.json`, 이어서 `python -m tools.benchmark_cpu_inference pipeline --threads 4 --mkldnn --output outputs/cpu-inference/pipeline-optimized.json`. 처음 만들었던 고정 프레임 목록을 두 실행에서 함께 사용한다.

## 재검토와 적용

전체 회귀 테스트 **293개 통과**, 변경분 공백 검사 통과. 스레드 수 제한·잘못된 설정 거절·라이브러리 초기화 후 스레드 복원·가속 초기화 실패·일부 결과 이후 가속 실패·비가속 실패 전달을 새 테스트로 검증했다.

앱을 완전히 종료하고 새 코드로 재시작하면 적용된다. 앱 재시작 후 실제 표시 시간과 게임 성능은 사용자 환경에서 추가 확인해야 한다. 전체 EXE 재빌드는 수행하지 않았다. 마지막 단계인 짧은 OBS 프레임 대기와 실제 공급 중단의 구분은 별도 승인 후 진행한다.
