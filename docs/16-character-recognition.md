# 캐릭터 영역 탐지·OCR·저장 연결

YOLO26n은 이름이 있는 사각형을 찾고 EasyOCR는 그 안의 글자를 읽는다. 이름마다 YOLO 클래스를 만드는 구조가 아니다. Swift에서 CGRect로 영역을 전달하고 별도의 문자열 인식 서비스가 String?을 반환하는 것과 같다.

`beatrice/character_vision.py`의 `CharacterVision.analyze(frame)`은 BGR 이미지 배열을 받는다. 이미지 파일, 영상, 향후 dxcam 모두 같은 함수를 호출한다. 현재는 3440×1440 전용이다. 초상화 아래 이름 주변과 변경 확인창 주변을 따로 잘라 **같은 YOLO26n 모델**에 입력한다. 잘라낸 좌표를 원본 좌표로 복원한 후 원본 픽셀로 OCR한다. 기존 관문 모델은 별도로 유지한다.

`beatrice/character.py`의 CharacterTracker는 SwiftUI의 상태 저장 객체에 해당한다. 현재 이름과 변경 대상 이름을 분리한다. 신뢰도 0.65 이상인 같은 이름이 3회 연속 관측되어야 현재 이름을 확정한다. OCR 원본·확대 결과가 서로 다르면 보류한다. 이 임계값은 개발용 설정이지 정확도 보증이 아니다. 알려진 이름으로 자동 치환하지 않는다.

변경 확인창을 탐지하면 기록을 보류하고, 변경 후 이름 영역이 사라졌다가 다른 현재 이름으로 다시 안정화될 때 갱신한다. 변경 대상은 접속 완료의 증거가 아니다. 팝업이 사라져도 기존 초상화가 남아 있는 경우는 취소인지 전환 대기인지 이 세 클래스만으로 구분할 수 없다. 이 경우 이전 이름을 이력으로 유지하되 기록은 계속 보류한다. 취소 후 기록 자동 재개, 캐릭터 선택 화면 경유, 감지를 시작하기 전에 이미 변경 중인 경우는 추가 장면 근거가 필요하다. 현재 구현을 모든 접속 경로의 완성으로 취급하지 않는다.

`CharacterRecordingBridge`는 확정된 이름을 기존 RecordingSession에 전달한다. 실제 characterKey, 진행 sessionID, 관문 수 등은 호출자가 resolve_context 함수로 제공한다. 이름만으로 서버나 새로운 레이드 진행을 추정하지 않는다. 변경 시 토큰을 교체하여 이전 캐릭터의 대기 프레임이 새 캐릭터로 기록되는 것을 막는다. 실시간 입력은 캡처 시점에 datetime.now(timezone.utc)와 당시 토큰을 프레임에 붙여야 한다. 이 모듈 자체는 영상의 상대 시각을 이벤트 저장 시각으로 변환하지 않는다.

## 실행

프로젝트 폴더에서 `.venv-ml`을 사용한다. 한국어 OCR 가중치가 없을 때만 `tools/prepare_character_ocr.py`를 실행한다. 일반 분석은 다운로드를 비활성화하고 로컬 가중치를 사용한다.

```bash
.venv-ml/bin/python tools/recognize_characters.py \
  '/Users/huisoo/Downloads/drive-download-20260916T083757Z-1-001/Lost Ark 2026.09.16 - 17.35.59.02.mp4' \
  --output outputs/character-recognition/success.json
.venv-ml/bin/python -m unittest discover -s tests -v
```

출력 JSON의 observation은 한 프레임에서 읽은 값이고 state는 연속 관측 후 판단이다. recordingAllowed=false이면 기록을 재개하지 않는다. ocr.raw에는 오독도 그대로 남겨 원인을 확인할 수 있다. videoSeconds는 영상 흐름을 검토하기 위한 상대 위치이며 실제 이벤트 날짜가 아니다. 이 실행 명령은 SQLite에 이벤트를 저장하지 않는다. 저장 연결은 별도 테스트에서 합성 관문 관측과 시간대를 명시한 테스트 날짜로 확인한다.

## 데이터와 검증 범위

승인된 6장·12박스에서 부분 이미지 12장을 만들었다. 이름 없는 부분 이미지 3장도 포함한다. train과 val은 같은 이미지이므로 학습 화면 재현 확인만 가능하다. 같은 영상에서 추출한 프레임으로 학습하고 해당 영상을 다시 실행한 결과도 독립 성능 평가가 아니다.

넓은 메뉴 ROI의 첫 학습에서는 작은 이름 탐지가 부족했다. 검수 박스 직접 OCR 실험에서도 테베체→테비체, 힐레우스→헬레우스 오독이 실제 발생했다. 따라서 불확실한 이름을 확정하지 않는 것이 필요하다. 현재 이름과 변경 대상 이름의 개별 인식 성능을 함께 살펴야 한다.

실행 환경은 macOS / Python 3.12이며 패키지 버전은 requirements-ml-macos-observed.txt에 보존한다. EasyOCR 설치로 opencv-python과 opencv-python-headless가 함께 설치되어 있다. 현재 명령 실행은 확인하지만 배포 환경에서는 같은 cv2 네임스페이스를 사용하는 이 두 패키지의 구성을 정리해야 한다. Windows 호환성·실시간 게임 성능은 아직 측정하지 않았다.

성공 영상의 대상 테베체는 OCR 신뢰도가 부족해 대상으로 확정하지 못했다. 그러나 접속 후 현재 이름 테베체를 읽어 갱신했다. 검수 이미지의 현재 이름 6개는 전처리 두 방식 모두 정답 문자열과 같았지만, 팝업에 가려진 2개는 신뢰도 기준 미달이었다. 대상 이름 3개 중 테베체와 힐레우스는 오독·신뢰도 미달로 보류했고 후이수는 읽었다. 목표 이름까지 모두 정확히 인식하는 단계는 아직 아니다.

Mac CPU에서 관측 1회 분석 시간 중앙값은 성공 영상 약 57ms, 취소 영상 약 52ms였다. 영상 디코딩·캡처·저장·게임 부하를 포함하는 지표가 아니며 Windows 실시간 성능을 의미하지 않는다. 영상 샘플링은 2Hz, 이름 확정은 연속 3회 관측이다.

기존 테스트와 신규 캐릭터 테스트 총 24개가 통과했다. `tools/check_character_storage.py`는 성공 영상의 실제 캐릭터 인식 결과를 저장 세션에 전달한 뒤, 합성 관문 전환과 명시적 테스트 시각을 넣어 테베체의 완료 기록 1건과 test_only 상태를 확인했다. 실제 레이드 완료를 영상에서 찾은 검증은 아니다. 임시 SQLite는 테스트 종료 시 정리하고 기록 내용은 outputs/character-recognition/storage-check.json에 남긴다.
