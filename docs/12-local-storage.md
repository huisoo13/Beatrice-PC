# 캐릭터별 SQLite 저장과 상태 복구

## 구현 구조

- `beatrice/storage.py`: SQLite 테이블과 원자적 저장. events는 기록, outbox는 전송 대기, sessions는 복구할 관문 상태다.
- `beatrice/session.py`: 캐릭터 확인 신호와 관문 분석을 연결한다. iOS의 공통 SessionStore처럼 현재 캐릭터를 보관한다.
- `tools/store_video_events.py`: 녹화 시작 절대시각과 테스트 캐릭터 확인 신호를 주입하여 기존 관측을 저장한다. YOLO 재학습·재추론은 없다.

외부 라이브러리 추가 없이 Python 기본 sqlite3로 구현했다. Core Data 저장처럼 트랜잭션으로 이벤트·대기열·체크포인트를 모두 저장하거나 모두 취소한다. DB 실패 시 메모리 상태도 갱신하지 않으므로 같은 프레임을 재시도할 수 있다. 이 버전은 하나의 분석 작업자가 순차 호출하는 구조이며 여러 프로세스가 같은 세션을 동시에 수정하는 용도가 아니다.

## 캐릭터 인식 연결 계약

1. 앱 시작은 미확인 상태다. 캐릭터 변경 시작 시 `begin_character_change()`를 호출해 확정을 중지한다.
2. 별도 인식 모듈이 확인한 캐릭터 식별자·이름·진행 세션·총 관문 수를 `confirm_character(...)`로 전달한다. 이때 해당 캐릭터·세션의 저장 상태를 복구한다.
3. 반환된 token을 이후 캡처 프레임에 붙이고 `observe(token, captured_at, boxes)`로 전달한다. 처리 시점이 아니라 캡처 시점의 토큰이어야 이전 캐릭터 대기 프레임이 새 캐릭터에게 섞이지 않는다.
4. 이름은 이벤트 생성 시 복사하여 이후 캐릭터 변경의 영향을 받지 않는다. characterKey는 인식/세션 관리 모듈이 제공하는 안정 식별자다. 같은 이름이 여러 서버에 존재할 경우를 고려해 이름 문자열만 전역 ID로 간주하지 않는다. 실제 식별자 구성은 후속 인식 모듈에서 결정한다.

현재 캐릭터명 자동 인식, 캐릭터 변경 감지, 진행 세션 자동 구분은 구현하지 않았다. 확인 신호가 올 때만 진행한다. 같은 캐릭터 확인 신호를 매 프레임 반복 호출하면 후보 횟수가 초기화되므로 상태 전환 시 호출해야 한다.

## 날짜와 시각

시간대가 포함된 datetime만 받는다. DB에는 ISO 8601 UTC로 저장하며 한국 표시 시 Asia/Seoul로 변환할 수 있다.

- observedAt: 완료 상태 후보를 처음 관측한 실제 날짜·시각.
- confirmedAt: 연속 유효 관측으로 확정한 날짜·시각.
- savedAt: PC에서 DB 저장을 시도한 날짜·시각(정확한 트랜잭션 커밋 순간은 아님).

녹화는 신뢰할 수 있는 녹화 시작 시각에 영상 경과 시간을 더한다. 파일 수정 시각이나 분석 실행 시각을 녹화 시각으로 대체하지 않는다. 실시간에서는 캡처 모듈이 실제 프레임 수신 시각을 전달한다. 이 시각은 게임 서버의 클리어 시각과 동일하다고 보장하지 않는다.

## 중복과 재시작

DB의 고유 조건은 characterKey + sessionID + gate다. 다른 캐릭터나 새 진행 회차의 같은 관문은 별도 기록할 수 있다. 같은 영상/진행을 재처리할 때 같은 sessionID를 사용한다. 새 진행에 새 sessionID를 발급하는 주체는 추후 세션 관리 모듈이다. DB 중복 방지가 잘못된 새 세션 판단까지 막지는 못한다.

안정 상태·슬롯·이미 완료한 관문·마지막 처리 시각을 저장한다. 재시작 시 미확인 상태로 출발하여 캐릭터와 동일 진행을 다시 확인해야 복구한다. 미확정 후보의 연속 횟수는 복구하지 않고 다시 세 번 확인한다. 이미 처리한 시각 이하 입력은 건너뛰므로 시계 역행도 무시된다. 실시간 시스템 시계 보정 정책은 후속 검증 대상이다.

## 테스트 실행

**다음 시각과 캐릭터는 가상 테스트 값이다. 실제 영상의 녹화 시각이나 실제 캐릭터명이 아니다.**

```bash
.venv/bin/python tools/store_video_events.py outputs/video002/observations.json \
  --db outputs/test-recordings.sqlite \
  --character-key test:character-A --character-name 테스트캐릭터A \
  --session-id test:video002 --expected-gates 2 \
  --recording-start 2026-09-16T09:00:00+09:00 --test-data

.venv/bin/python -m unittest discover -s tests -v
```

isTest=true, timeBasis=synthetic_test, outbox.status=test_only로 표시된다. 미래 업로더는 pending만 전송해야 하며 test_only는 제외한다. 정상 시각을 알고 실제 캐릭터가 확인된 녹화만 --test-data 없이 사용한다. Google Drive 업로더는 아직 없으므로 어떤 기록도 전송되지 않았다.

실행 결과, A 첫 실행은 1건, 다시 실행은 0건 추가, B는 1건 추가였다. 테스트 DB에는 캐릭터별 총 2건이다. 가상 한국 시각으로 관측 2026-09-16 09:00:10.215767, 확정 09:00:10.615522이며 UTC에는 00:00:10으로 저장된다. 기존 8개와 추가 저장 관련 9개, 총 17개 테스트가 통과했다. DB 실패 시 전부 롤백·재시도, 캐릭터 변경 전 프레임 거부, 다른 캐릭터/새 회차, 재시작 복구를 검증했다.

## 남은 범위

OCR을 미룬 상태라 dungeonName/difficulty는 null, contextStatus=ocr_pending으로 보존한다. 관문 이벤트 저장 경로 검증이며 최종 데이터의 모든 필드를 완성한 것은 아니다. 실제 배포 전에는 던전·난이도를 포함한 필수 문맥 검증과 업로드 가능 여부를 연결해야 한다. SQLite 운영 마이그레이션은 현재 버전 1만 지원한다. Windows 게임 캡처·강제 종료 복구·디스크 고갈·동기화는 실제 환경에서 추가 검증해야 한다.
