# OBS 프레임 대기 처리 개선

2026-10-06. 사용자의 승인에 따라 OCR 일괄 제출, CPU 추론 최적화에 이어 마지막 단계인 OBS 프레임 대기 처리를 개선했다.

## 문제와 변경

이전에는 공유 메모리를 쓰는 순간과 읽는 순간이 겹치거나 이미 읽은 게시물을 다시 확인한 경우에도 캡처 중단으로 처리했다. 매번 0.5초를 기다리고 캐릭터·던전·완료의 연속 확인 횟수를 초기화했다.

이제 캡처 결과를 다음과 같이 구분한다.

| 상황 | 처리 |
| --- | --- |
| 잠깐의 새 게시물 대기·쓰기 중·복사 충돌 | 10ms 후 재시도. 중단 메시지와 인식 상태 초기화 없음 |
| OBS 공급 중단 | 마지막 정상 게시물의 전달 시각이 2초 이상 오래됐고 읽기 실패도 250ms 이상 지속될 때 중단 처리 |
| 읽기 충돌 직전 분석이 오래 걸린 경우 | 최소 250ms의 읽기 재시도 기회를 줘 실제 공급 중단인지 구분 |
| 오래된 프레임·검은 화면·최소화 중 동일 픽셀·2초 이상 동일 화면 | 기존 분석 보류 유지. 기다리는 동안 다른 읽기 충돌이 발생해도 해당 보류 사유 유지 |
| 실제 중단 후 유효 프레임 복귀 | 분석 재개. 이전 게시물을 새 관측으로 재사용하지 않음 |

실제 중단에서는 연속 확인 후보를 한 번 초기화하되 확정된 캐릭터와 완료 중복 방지 상태를 보존한다. 같은 중단 사유는 반복 표시하지 않는다. 실제 중단 상태에서는 100ms 간격으로 재확인한다. 이 재확인 간격과 10ms 읽기 재시도는 분석 주기 변경이 아니며, 기존 0.5초 목표 분석 주기는 유지한다.

`capture.readWaits`에 `not_ready`, `writer_busy`, `already_read`, `copy_race`의 누적 횟수를 남긴다. 다음 유효 프레임의 기존 진단 JSON에 포함되므로 대기가 자주 발생하는 이유를 확인할 수 있다.

## 검증

- 전체 회귀 테스트 **301개 통과**, 변경분 공백 검사 통과.
- 짧은 대기 뒤 세 번째 캐릭터 관측으로 정상 확정되는 것을 검증했다. 대기 자체는 관측 횟수를 증가시키지 않는다.
- 실제 공급 중단에서는 연속 후보를 초기화하고, 확정된 이름과 이미 소비한 완료 표시의 중복 방지 상태를 유지하는 것을 검증했다.
- 쓰기 중·복사 도중 재게시·장시간 분석 후 첫 읽기 실패·공급 중단과 복귀·검은 화면 사유 유지·같은 중단의 반복 알림 방지를 검증했다.
- 앱에 포함한 libobs의 내부 색상 소스로 **3440×1440** 프레임 전달, 콜백 중단, 재등록 후 복귀를 실측했다. 일반 읽기 대기는 `transient`로 처리하고, 공급을 멈추면 마지막 전달 후 약 2초에 실제 중단으로 전환했다. 새 유효 프레임이 오면 `ready`로 복귀했다.
- 최종 실측: 정상 구간 14개, 복귀 구간 14개 유효 프레임. 읽기 대기 352회는 이미 읽은 게시물 확인이었다. 공급 중단 전환은 중단 단계 시작 약 1.906초에 발생했다. 시작 전 프레임 준비와 복귀 직후 기존 픽셀 보류도 정상 유지됐다.

재현: `python -m tools.probe_obs_wait`. 결과는 `outputs/embedded-obs-probe/wait-test.json`, 로그는 `wait-test.log`에 있다. 내부 시험 소스 검증이며 실제 게임 창·포커스·최소화를 조작하거나 완료 DB에 기록하지 않았다. 실제 게임에서 메시지 빈도와 완료 인식 개선은 앱 재시작 후 추가 확인할 수 있다.

## 적용

요청한 세 단계 작업을 모두 완료했다. 앱을 완전히 종료하고 새 코드로 재시작하면 OCR 일괄 제출·CPU 가속·프레임 대기 개선이 적용된다. 모델 파일·클래스·인식 해상도·확정 조건을 변경하지 않았다. 전체 EXE 재빌드는 수행하지 않았다.
