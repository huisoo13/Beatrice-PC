# Google Drive JSON 저장·불러오기

2026-10-08: 현재 WinUI 설정에서 Google 로그인·Drive 권한 연결·저장·불러오기를 제공합니다. 자동 업로드는 `drive_service.py`에서 실행하며, 기존 Qt 화면 코드는 제거했습니다. JSON의 7개 필드는 유지하며, PC 전용 단일 파일과 주간 초기화 정책을 적용합니다. [이전 구조와 검증](59-native-drive-migration.md)을 참고합니다.

2026-09-27. 메인 창에 `Drive 권한 연결`, `Drive에 저장`, `Drive에서 불러오기`를 추가했습니다.
기존 Google 로그인 사용자는 Drive 권한 연결을 한 번 승인합니다. 신규 로그인은
`openid email profile https://www.googleapis.com/auth/drive.appdata`를 요청합니다.
Drive 권한 연결 시 기존 계정과 다른 계정을 선택하면 적용하지 않습니다.

## 사용 방법

1. 앱을 완전히 재시작합니다. 로그인 상태가 복원됩니다.
2. 권한이 없다면 `Drive 권한 연결`에서 앱 전용 데이터 접근에 동의합니다.
3. `Drive에 저장`을 누르면 현재 확정 기록의 JSON을 생성하고, 서버에서 다시 읽어 내용 일치를 확인합니다.
4. `Drive에서 불러오기`를 누르면 분석이 안전하게 보류된 뒤 `PC.json`을 읽습니다. 복원·취소·실패 후 게임이 있으면 분석을 자동 재개합니다. 게임이 없는 상태에서 시작한 복원 중에도 새로 감지된 게임의 분석은 보류합니다.
5. 로그인 계정·저장 시각·Drive와 PC의 기록 수를 확인하고 적용하면 PC 기록을 교체합니다.

수동 백업·복원과 새 완료 기록의 자동 업로드를 지원합니다. 여러 장치의 변경 병합이나 자동 다운로드는 하지 않습니다.
빈 완료 이력은 업로드하지 않습니다. 주간 초기화만으로 Drive 업로드를 예약하지 않습니다. 캐릭터/던전/난이도 미확정과 명시적인 테스트 기록은 제외합니다.
교체 전 로컬 백업을 보존하고 교체 뒤 서버 읽기로 검증합니다. 응답 유실 시 서버 반영 여부가 불확실할 수 있으며 재시도는 같은 PC 파일을 갱신합니다.
새 완료 기록의 미전송 상태는 로컬 DB에 보존하며 네트워크 오류 때 자동 업로드를 재시도합니다.
작업 중에는 계정 변경·로그아웃·로컬 삭제·새 분석 시작·새로고침을 막습니다.
종료 시 진행 중인 업로드·검증이 끝날 때까지 기다리고 다운로드는 취소합니다.

## 새 완료 기록 자동 저장

- 캐릭터·던전·난이도가 확인된 기록이 새로 `완료`로 저장되면 Drive 업로드를 예약합니다.
- 관문 아이콘, 완료 배너, 후속 관문 완료 보완, 캐릭터 미확정 기록의 사후 확정 모두 기존 저장 경로에서 처리합니다.
- `진행 전`/`진행중`만 변경되거나 같은 완료를 다시 관측하면 예약하지 않습니다.
- 명시적인 `isTest=true` 또는 `synthetic_test` 기록은 기존 정책대로 제외합니다. 과거 테스트 표시는 자동으로 수정하지 않습니다.
- 변경을 약 3초 모아 현재 전체 기록의 JSON을 자동 업로드합니다. 계속 변경되는 경우 최대 약 15초마다 시작합니다.
- 로그인·Drive 권한이 없으면 대기합니다. 앱이 실행 중이고 권한이 확인되면 자동으로 이어집니다.
- 업로드 실패는 5·10·20·40초… 최대 5분 간격으로 재시도합니다. 재시도 전에 앱을 종료해도 대기 상태는 보존됩니다.
- 저장 확인 이후에만 해당 Google 계정의 전송 완료 상태를 기록합니다. 업로드 도중 추가된 완료는 다음 전송에 남습니다.
- JSON 내용과 변경 번호를 동일한 SQLite 읽기 트랜잭션에서 가져와 동시 기록 시 누락을 막습니다.
- 앱 재실행이나 주간 초기화만으로 새 업로드를 만들지 않습니다. 이전 실행의 미전송 기록은 재시도하며, 최초 전체 이력 복구 시에는 복구된 이력의 업로드를 예약합니다.
- 기록 전체 삭제와 Drive 복원은 이전 자동 업로드 대기를 초기화하며, 해당 동작 자체를 자동 전송하지 않습니다.
- PC는 `PC.json` 하나를 생성하고 이후에는 같은 파일 ID에 내용을 갱신합니다. iOS 파일은 수정하지 않습니다.
  기존 PC 파일을 교체하기 전 `drive-backups/PC-*.json`에 내용을 저장·검증하며 백업 실패 시 교체하지 않습니다.

화면에 `Drive 자동 저장·읽기 검증 완료`가 표시되면 서버에서 다시 읽은 내용까지 일치한 상태입니다.

## iOS와 공유할 파일 계약 (schemaVersion 3)

- 같은 Google Cloud 프로젝트의 플랫폼별 OAuth 클라이언트와 같은 Google 계정을 사용합니다.
- 파일 저장 공간은 `appDataFolder`, MIME 형식은 `application/json`입니다.
- PC 파일 이름은 `PC.json`, iOS의 별도 파일 이름은 `iOS.json`입니다. 각 플랫폼은 자신의 파일만 씁니다.
- 파일 메타데이터: `appProperties: {"beatriceRecords": "v1", "schemaVersion": "3"}`.
- PC 목록 쿼리: `trashed = false and appProperties has { key='beatriceRecords' and value='v1' } and name = 'PC.json'`.
- `spaces=appDataFolder`, `orderBy=createdTime desc`로 조회합니다. 다운로드는 `files.get`의 `alt=media`입니다.
- 최초 업로드는 `files.create` multipart, 이후에는 같은 파일 ID로 `files.update` multipart PATCH입니다.
- 운영 PC 업로드는 이전 랜덤 파일이나 `iOS.json`을 수정·삭제하지 않습니다. 기존 랜덤 파일의 자동 정리는 없습니다.
- 실제 연결 검사용 `integration-test` 영역은 독립된 새 파일 방식으로 유지합니다.
- JSON 최상위는 배열이며 기존 다섯 항목에 `recordID`, `updatedAt`을 추가합니다.
  새 앱은 기존 다섯 항목짜리 JSON과 schemaVersion 1·2 파일도 불러옵니다. iOS는 schemaVersion 3과 새 완료 ID 규칙을 지원해야 합니다.

```json
[
  {
    "characterName": "테스트",
    "dungeonName": "던전",
    "difficulty": "하드",
    "gate": 1,
    "state": "완료",
    "recordID": "br2_57d7461f080342ddaf2e64e6d32a93f5",
    "updatedAt": "2026-10-08T01:00:00.000Z"
  }
]
```

UTF-8, 최대 4 MiB/10,000행입니다. 현재 내보내기 상태는 `완료`만 포함합니다. 과거 `진행 전`, `진행중`도 읽기 검증은 지원하지만 로컬 복원에서는 제외합니다.
관문은 정수 1~8이며 완료된 관문만 포함하므로 전체 관문 배열을 요구하지 않습니다. 저장된 완료 행 수를 전체 관문 수로 해석하지 않습니다. [완료만 저장 정책](39-completion-only-storage.md)을 참고합니다.
관문 구분이 없는 레이드 전체는 `gate: 0` 한 행으로 표시합니다.
PC 내부에서는 이를 기존 슬롯 1과 `completionScope: raid`로 변환합니다.
새 완료는 `br2_` + UUID4 소문자 32자리 hex ID를 생성합니다. 같은 주의 중복 관측은 추가 저장하지 않습니다.
다음 주 같은 캐릭터·던전·관문을 다시 완료하면 새 ID로 별도 이력이 추가됩니다. 이미 저장된 완료의 ID는 재실행·업로드·복원으로 바뀌지 않습니다.
JSON 안에서 중복 ID가 있으면 최신 updatedAt 행을 선택합니다. 시각과 내용까지 같으면 한 행으로 합칩니다.
같은 시각인데 내용이 다르면 임의 선택하지 않고 파일 적용을 거부합니다.
난이도가 다르더라도 같은 관문에 별도 행을 둘 수 없고, 서로 다른 관문의 난이도는 달라도 됩니다.
던전명 정규화는 NFC 후 공백과 `, : [ ]` 제거입니다. 사용자 입력 필드는 비어 있으면 안 됩니다.

### 기존 br1 recordID 호환 규칙

아래 결정적 ID는 기존 기록을 읽을 때만 사용합니다. 새 완료는 위의 br2 UUID 규칙을 사용합니다. 캐릭터명은 입력 문자열 그대로 사용하고, 던전명만 위 규칙으로 정규화합니다.
관문은 선행 0 없는 십진 문자열(관문 없는 레이드는 `0`)입니다.

1. 바이트 배열을 UTF-8 `beatrice-record-v1\n`으로 시작합니다. 끝의 `\n`은 실제 LF 한 바이트입니다.
2. 캐릭터명, 정규화한 던전명, 관문 문자열 순서로 각 UTF-8 바이트를 만듭니다.
3. 각 항목마다 `UTF-8 바이트 길이의 십진 ASCII` + `:` + `UTF-8 바이트`를 붙입니다.
4. 전체 바이트의 SHA-256을 소문자 64자리 hex로 변환하고 앞에 `br1_`을 붙입니다.

문자 개수가 아닌 UTF-8 **바이트 길이**를 사용합니다. `테스트 / 던전 / 1`의 기존 br1 고정 검증값은 `br1_484a542054cff3d5084717252fe53348a525e41428b2f5d3db47c0e4ed4a67a7`입니다.
난이도·상태·updatedAt은 ID 계산에 넣지 않습니다. 주차를 ID나 JSON에 추가하지 않습니다. 새 주의 새 완료는 독립된 br2 ID를 부여하며 주차 표시를 추가하지 않습니다.

### updatedAt와 기존 데이터

- UTC ISO 8601 밀리초 형식으로 저장합니다. 입력 시 명시적인 UTC 오프셋도 허용하고 UTC로 통일합니다.
- 로컬 저장 내용이 실제로 변경될 때 갱신하며, 같은 관측을 반복하거나 단순 업로드·재실행·복원할 때는 유지합니다.
- 난이도 변경도 미완료 기록의 수정으로 취급합니다. 이미 완료된 행은 기존 인식 정책대로 화면 재관측으로 덮어쓰지 않습니다.
- 로컬 시계가 뒤로 가더라도 같은 기록의 직전 updatedAt보다 최소 1밀리초 뒤로 설정합니다.
- 기존 SQLite 행은 ID를 계산하고 `savedAt → confirmedAt → observedAt` 순서의 유효 시각으로 보완합니다.
  이 보완만으로는 자동 업로드를 예약하지 않습니다. 다음 수동/자동 저장부터 새 필드를 포함합니다.
- 시각 없는 구형 JSON은 `1970-01-01T00:00:00.000Z`를 '시각 미상' 값으로 사용합니다. 복원 시각을 수정 시각으로 꾸미지 않습니다.
- 기존 br1 ID는 내용과의 일치를 검증하고, 새 br2 ID는 정해진 형식을 검증합니다. recordID/updatedAt 중 한 필드만 있는 파일도 거부합니다.
- 수정 시각은 PC/iOS 시계 기준입니다. 서로 다른 장치의 시계 오차까지 해결하는 동기화 규칙은 아닙니다.
- Drive 불러오기는 기존처럼 확인 후 로컬 스냅샷을 교체합니다. 로컬과 원격 전체를 자동 병합하는 기능은 아직 없습니다.

## 주간 반복 초기화와 완료 이력 유지

주간 기준은 기기 시간대와 관계없이 한국 시간 수요일 **오전 6시**입니다.
예를 들어 2026-10-07 06:00 KST는 `2026-10-06T21:00:00.000Z`입니다.
PC는 실행 중 약 1초 간격으로 경계를 확인하고 분석 작업자가 멈춘 뒤 이번 주 중복 완료 판정만 초기화합니다.
앱이 꺼져 있으면 다음 실행 시 현재 주 기준을 적용합니다. 다운로드 확인창이 열려 있으면 해당 작업을 마친 뒤 초기화합니다.

**완료 기록을 초기화하거나 화면·Drive에서 제외하지 않습니다.**
`records.sqlite3`의 `completion_history`는 전체 완료 이력이고, `gate_states`는 이번 주 인식용 체크포인트입니다.
주간 경계는 로컬 `weekly_repeat`에만 저장합니다. 경계 이전 체크포인트를 현재 반복 판정에서 제외하고 분석 추적기를 새로 구성합니다.
다음 주 다시 완료하면 새 ID로 이력이 추가되고 해당 관문의 체크포인트를 갱신합니다.
기존 이력의 ID·updatedAt, 업로드 배열, 미전송 변경 번호와 전송 확인은 주간 초기화로 바뀌지 않습니다.
JSON에는 weekID/reset/deleted 같은 별도 표식을 넣지 않습니다. 초기화만으로 빈 JSON이나 별도 Drive 업로드가 발생하지 않습니다.

이전 구현이 만든 `weekly-records/*.sqlite3`가 있다면 최초 실행 때 모든 주의 완료 이력을 복구하고 기존 파일은 보존합니다.
구형 br1 ID가 서로 다른 주에 반복된 경우 후속 발생에 안정적인 br2 ID를 부여해 이력이 합쳐지지 않도록 합니다.
복구한 전체 이력은 자동 업로드 대상으로 예약합니다. 소스별 복구 표식을 로컬 DB에 저장해 재실행 시 중복 복구하지 않습니다.

iOS는 별도 프로젝트에서 다음 가져오기 규칙을 적용해야 합니다. PC의 참조 구현은 `drive_data.merge_records(local, incoming)`입니다.

1. PC.json에서 전체 완료 이력을 읽습니다. 과거 주라는 이유로 제외하거나 삭제하지 않습니다.
2. 없는 recordID는 추가합니다. 같은 ID는 incoming.updatedAt이 더 최신일 때만 기록 내용을 갱신합니다.
3. 같은 시각과 같은 내용은 그대로 유지하고, 같은 시각에 다른 내용이면 충돌로 처리합니다.
4. PC 파일에 없는 행도 기존 iOS 이력에 유지합니다. 사용자 확인 표시는 recordID별 iOS 전용 상태로 보존합니다.
5. 결과는 iOS.json에만 저장합니다. 주간 반복 상태가 필요하면 완료 이력·확인 표시와 분리해 관리합니다.

전체 이력이 누적되므로 PC.json의 크기도 점차 증가합니다. 업로드 횟수에 따라 별도 Drive 파일이 늘어나지는 않습니다.
현재 최대 4 MiB/10,000행 제한은 유지하며, 제한 초과 시 기존 파일을 교체하지 않고 저장 오류를 표시합니다.
주간 20행이면 연간 약 1,040행입니다. 기록 이름 길이에 따라 다르지만 일반적인 이름은 연간 대략 250 KiB 수준입니다.

## 로컬 복원 보호

JSON 전체 검증을 통과한 후에만 적용합니다. UI에서 분석 작업자의 정지 완료를 확인합니다.
복원 전 SQLite Backup API로 WAL을 포함한 전체 DB를 데이터 폴더의 `drive-backups/*.sqlite3`에 보관합니다.
백업 실패 시 복원하지 않습니다. 전체 테이블 초기화와 관문 상태 삽입은 한 트랜잭션이며 실패하면 롤백합니다.
인식 모델·설정·Google 로그인은 유지합니다. 캐릭터 미확정 임시 기록과 과거 중복 방지 이력은 복원 때 초기화합니다.
JSON에는 관측 시각이 없으므로 복원된 행의 표시 시각은 불러온 시각이며 `(불러옴)`과 `Google Drive`로 표시합니다.
별도 updatedAt은 파일의 원래 수정 시각을 유지합니다.

## 검증

- `tests/test_google_drive.py`: JSON 왕복, 관문 없는 레이드, 중복/손상/용량 제한,
  미확정·테스트 제외, WAL 백업, 복원 실패 롤백, 업로드 실패 보존, 페이지 조회,
  계정·권한·네트워크·취소, UI 적용/취소와 분석 중 차단을 검증합니다.
- 실제 Google 계정으로 `tools/check_drive_connection.py --authorize` 실행 성공:
  테스트 JSON 생성 → 앱 전용 공간 목록 조회 → 다운로드 일치 → 해당 테스트 파일 삭제.
  테스트 전용 `appProperties.beatriceRecords=integration-test`를 사용해 실제 기록 목록과 분리합니다.
- 위 실제 연결 검사에서는 운영 게임 기록을 업로드하거나 로컬 DB를 복원하지 않습니다.
- 자동 저장 추가 후 전체 192개 테스트 통과. `tests/test_auto_upload.py`에서 완료 트리거, 중복 억제,
  대기 상태 재실행 유지, 동일 트랜잭션 롤백, 동시 기록, 지연·재시도, 계정·권한·복원 동작을 검증했습니다.
- `tools/check_auto_drive.py`의 임시 DB에서 1관문·2관문 완료를 차례로 저장하고 실제 Drive 자동 업로드 및
  최신 JSON 반영을 확인했습니다. 같은 완료 재관측은 업로드를 예약하지 않았으며 테스트 파일 2개를 삭제했습니다.
- recordID/updatedAt 추가 후 전체 201개 테스트 통과. 실제 Drive에서도 상태 변경 전후의 ID 유지,
  변경된 행만 수정 시각 갱신, 이전 행 시각 유지와 중복 전송 억제를 확인하고 테스트 파일을 삭제했습니다.

추가 검증: `tests/test_weekly.py`와 Host 테스트에서 주간 경계, 화면·Drive 전체 이력 유지, 미전송 상태 유지, 새 주 동일 관문의 별도 ID, 재실행·복원, 과거 주별 DB 복구, 최신 시각 비교를 검증합니다. 전체 Python 테스트 342개 통과. 실게임 중 운영 계정의 전송 확인 리비전이 현재 변경 리비전과 일치하는 것을 로컬 DB에서 확인했습니다. 운영 서버의 현재 파일을 별도 검사 도구로 다시 다운로드하지는 않았습니다.
