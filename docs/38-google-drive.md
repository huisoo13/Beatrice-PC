# Google Drive JSON 저장·불러오기

2026-09-27. 메인 창에 `Drive 권한 연결`, `Drive에 저장`, `Drive에서 불러오기`를 추가했습니다.
기존 Google 로그인 사용자는 Drive 권한 연결을 한 번 승인합니다. 신규 로그인은
`openid email profile https://www.googleapis.com/auth/drive.appdata`를 요청합니다.
Drive 권한 연결 시 기존 계정과 다른 계정을 선택하면 적용하지 않습니다.

## 사용 방법

1. 앱을 완전히 재시작합니다. 로그인 상태가 복원됩니다.
2. 권한이 없다면 `Drive 권한 연결`에서 앱 전용 데이터 접근에 동의합니다.
3. `Drive에 저장`을 누르면 현재 확정 기록의 JSON을 생성하고, 서버에서 다시 읽어 내용 일치를 확인합니다.
4. 분석을 정지한 뒤 `Drive에서 불러오기`를 누르면 가장 최근 서버 생성 시각의 백업을 읽습니다.
5. 로그인 계정·저장 시각·Drive와 PC의 기록 수를 확인하고 적용하면 PC 기록을 교체합니다.

수동 백업·복원과 새 완료 기록의 자동 업로드를 지원합니다. 여러 장치의 변경 병합이나 자동 다운로드는 하지 않습니다.
빈 로컬 기록은 업로드하지 않습니다. 캐릭터/던전/난이도 미확정과 명시적인 테스트 기록은 제외합니다.
저장 실패 시 기존 클라우드 파일을 수정하거나 삭제하지 않습니다.
새 완료 기록의 미전송 상태는 로컬 DB에 보존하며 네트워크 오류 때 자동 업로드를 재시도합니다.
작업 중에는 계정 변경·로그아웃·로컬 삭제·새 분석 시작·새로고침을 막습니다.
종료 요청은 Drive 작업 완료 후 다시 할 수 있습니다.

## 새 완료 기록 자동 저장

- 캐릭터·던전·난이도가 확인된 기록이 새로 `완료`로 저장되면 Drive 업로드를 예약합니다.
- 관문 아이콘, 완료 배너, 후속 관문 완료 보완, 캐릭터 미확정 기록의 사후 확정 모두 기존 저장 경로에서 처리합니다.
- `진행 전`/`진행중`만 변경되거나 같은 완료를 다시 관측하면 예약하지 않습니다.
- 명시적인 `isTest=true` 또는 `synthetic_test` 기록은 기존 정책대로 제외합니다. 과거 테스트 표시는 자동으로 수정하지 않습니다.
- 변경을 약 3초 모아 현재 전체 기록의 JSON을 자동 업로드합니다. 계속 변경되는 경우 최대 약 15초마다 시작합니다.
- 로그인·Drive 권한이 없으면 대기합니다. 앱이 실행 중이고 권한이 확인되면 자동으로 이어집니다.
- 업로드 실패는 5·10·20·40초… 최대 5분 간격으로 재시도합니다. 재시도 전에 앱을 종료해도 대기 상태는 보존됩니다.
- 저장 확인 이후에만 해당 Google 계정의 전송 완료 상태를 기록합니다. 업로드 도중 추가된 완료는 다음 전송에 남습니다.
- JSON 내용과 변경 번호를 동일한 SQLite 읽기 트랜잭션에서 가져와 동시 기록 시 누락을 막습니다.
- 기존 기록을 처음 읽거나 앱을 재실행한 사실만으로 새 업로드를 만들지 않습니다. 단, 이전 실행의 미전송 기록은 재시도합니다.
- 기록 전체 삭제와 Drive 복원은 이전 자동 업로드 대기를 초기화하며, 해당 동작 자체를 자동 전송하지 않습니다.
- 저장 방식은 기존 파일 계약과 같습니다. 매번 새 JSON 스냅샷을 만들어 최신 파일을 갱신하고 이전 파일은 보존합니다.
  네트워크 응답 유실 직후 재시도에서는 내용이 같은 스냅샷이 추가로 생길 수 있습니다.

화면에 `Drive 자동 저장·읽기 검증 완료`가 표시되면 서버에서 다시 읽은 내용까지 일치한 상태입니다.

## iOS와 공유할 파일 계약 (schemaVersion 2)

- 같은 Google Cloud 프로젝트의 플랫폼별 OAuth 클라이언트와 같은 Google 계정을 사용합니다.
- 파일 저장 공간은 `appDataFolder`, MIME 형식은 `application/json`입니다.
- 파일 이름은 `beatrice-records-v1-<random>.json`입니다. 매 저장마다 새 파일을 만듭니다.
- 파일 메타데이터: `appProperties: {"beatriceRecords": "v1", "schemaVersion": "2"}`.
  `beatriceRecords=v1`은 기존 파일도 찾기 위한 저장 공간 구분이며 JSON 스키마 버전과 별개입니다.
- 목록 쿼리: `trashed = false and appProperties has { key='beatriceRecords' and value='v1' }`.
- `spaces=appDataFolder`, `orderBy=createdTime desc`로 조회해 가장 최근 파일을 읽습니다.
- 다운로드는 `files.get`의 `alt=media`, 업로드는 `files.create` multipart입니다.
- 이전 파일을 보존합니다. 여러 장치가 동시에 저장하면 서버에서 나중에 생성된 파일이 최신입니다.
  기존 파일 내용을 수정하는 방식은 이 계약에 포함하지 않습니다. 과거 백업 선택·정리는 후속 기능입니다.
- JSON 최상위는 배열이며 기존 다섯 항목에 `recordID`, `updatedAt`을 추가합니다.
  새 앱은 기존 다섯 항목짜리 JSON도 불러옵니다. iOS도 새 필드와 아래 ID 규칙을 적용해야 합니다.

```json
[
  {
    "characterName": "테스트",
    "dungeonName": "던전",
    "difficulty": "하드",
    "gate": 1,
    "state": "완료",
    "recordID": "br1_484a542054cff3d5084717252fe53348a525e41428b2f5d3db47c0e4ed4a67a7",
    "updatedAt": "2026-09-27T01:00:00.000Z"
  }
]
```

UTF-8, 최대 4 MiB/10,000행입니다. 상태는 `진행 전`, `진행중`, `완료`입니다.
관문은 정수 1~8이며 던전별 전체 관문 배열을 포함합니다.
관문 구분이 없는 레이드 전체는 `gate: 0` 한 행으로 표시합니다.
PC 내부에서는 이를 기존 슬롯 1과 `completionScope: raid`로 변환합니다.
기존 PC 저장 키와 같이 캐릭터명·정규화된 던전명·관문이 같으면 같은 recordID입니다.
JSON 안에서 중복 ID가 있으면 최신 updatedAt 행을 선택합니다. 시각과 내용까지 같으면 한 행으로 합칩니다.
같은 시각인데 내용이 다르면 임의 선택하지 않고 파일 적용을 거부합니다.
난이도가 다르더라도 같은 관문에 별도 행을 둘 수 없고, 서로 다른 관문의 난이도는 달라도 됩니다.
던전명 정규화는 NFC 후 공백과 `, : [ ]` 제거입니다. 사용자 입력 필드는 비어 있으면 안 됩니다.

### recordID 생성 규칙

UUID를 사용하지 않습니다. 캐릭터명은 입력 문자열 그대로 사용하고, 던전명만 위 규칙으로 정규화합니다.
관문은 선행 0 없는 십진 문자열(관문 없는 레이드는 `0`)입니다.

1. 바이트 배열을 UTF-8 `beatrice-record-v1\n`으로 시작합니다. 끝의 `\n`은 실제 LF 한 바이트입니다.
2. 캐릭터명, 정규화한 던전명, 관문 문자열 순서로 각 UTF-8 바이트를 만듭니다.
3. 각 항목마다 `UTF-8 바이트 길이의 십진 ASCII` + `:` + `UTF-8 바이트`를 붙입니다.
4. 전체 바이트의 SHA-256을 소문자 64자리 hex로 변환하고 앞에 `br1_`을 붙입니다.

문자 개수가 아닌 UTF-8 **바이트 길이**를 사용합니다. 위 JSON의 ID는 `테스트 / 던전 / 1`의 고정 검증값입니다.
난이도·상태·updatedAt은 ID 계산에 넣지 않습니다. 주간 초기화 회차는 아직 포함하지 않으며 후속 버전에서 다룹니다.

### updatedAt와 기존 데이터

- UTC ISO 8601 밀리초 형식으로 저장합니다. 입력 시 명시적인 UTC 오프셋도 허용하고 UTC로 통일합니다.
- 로컬 저장 내용이 실제로 변경될 때 갱신하며, 같은 관측을 반복하거나 단순 업로드·재실행·복원할 때는 유지합니다.
- 난이도 변경도 미완료 기록의 수정으로 취급합니다. 이미 완료된 행은 기존 인식 정책대로 화면 재관측으로 덮어쓰지 않습니다.
- 로컬 시계가 뒤로 가더라도 같은 기록의 직전 updatedAt보다 최소 1밀리초 뒤로 설정합니다.
- 기존 SQLite 행은 ID를 계산하고 `savedAt → confirmedAt → observedAt` 순서의 유효 시각으로 보완합니다.
  이 보완만으로는 자동 업로드를 예약하지 않습니다. 다음 수동/자동 저장부터 새 필드를 포함합니다.
- 시각 없는 구형 JSON은 `1970-01-01T00:00:00.000Z`를 '시각 미상' 값으로 사용합니다. 복원 시각을 수정 시각으로 꾸미지 않습니다.
- 입력 ID가 내용에서 계산한 ID와 다르면 거부합니다. recordID/updatedAt 중 한 필드만 있는 파일도 거부합니다.
- 수정 시각은 PC/iOS 시계 기준입니다. 서로 다른 장치의 시계 오차까지 해결하는 동기화 규칙은 아닙니다.
- Drive 불러오기는 기존처럼 확인 후 로컬 스냅샷을 교체합니다. 로컬과 원격 전체를 자동 병합하는 기능은 아직 없습니다.

## 로컬 복원 보호

JSON 전체 검증을 통과한 후에만 적용합니다. UI에서 분석 작업자의 정지 완료를 확인합니다.
복원 전 SQLite Backup API로 WAL을 포함한 전체 DB를 데이터 폴더의 `drive-backups/*.sqlite3`에 보관합니다.
백업 실패 시 복원하지 않습니다. 전체 테이블 초기화와 관문 상태 삽입은 한 트랜잭션이며 실패하면 롤백합니다.
인식 모델·설정·Google 로그인은 유지합니다. 캐릭터 미확정 임시 기록과 과거 중복 방지 이력은 복원 때 초기화합니다.
JSON에는 관측 시각이 없으므로 복원된 행의 표시 시각은 불러온 시각이며 `(불러옴)`과 `Google Drive`로 표시합니다.
별도 updatedAt은 파일의 원래 수정 시각을 유지합니다.

- `tests/test_google_drive.py`: JSON 왕복, 관문 없는 레이드, 중복/손상/용량 제한,
  미확정·테스트 제외, WAL 백업, 복원 실패 롤백, 업로드 실패 보존, 페이지 조회,
  계정·권한·네트워크·취소, UI 적용/취소와 분석 중 차단을 검증합니다.
- 실제 Google 계정으로 `tools/check_drive_connection.py --authorize` 실행 성공:
  테스트 JSON 생성 → 앱 전용 공간 목록 조회 → 다운로드 일치 → 해당 테스트 파일 삭제.
  테스트 전용 `appProperties.beatriceRecords=integration-test`를 사용해 실제 기록 목록과 분리합니다.
- 위 실제 연결 검사에서는 운영 게임 기록을 업로드하거나 로컬 DB를 복원하지 않습니다.
- 자동 저장 추가 후 전체 192개 테스트 통과. `tests/test_auto_upload.py`에서 완료 트리거, 중복 억제,
  대기 상태 재실행 유지, 동일 트랜잭션 롤백, 동시 기록, 지연·재시도, 계정·권한·복원 동작을 검증했습니다.
- `tools/check_auto_drive.py`의 임시 DB에서 1관문·2관문 완료를 차례로 저장하고 실제 Drive 자동 업로드 및
  최신 JSON 반영을 확인했습니다. 같은 완료 재관측은 업로드를 예약하지 않았으며 테스트 파일 2개를 삭제했습니다.
- recordID/updatedAt 추가 후 전체 201개 테스트 통과. 실제 Drive에서도 상태 변경 전후의 ID 유지,
  변경된 행만 수정 시각 갱신, 이전 행 시각 유지와 중복 전송 억제를 확인하고 테스트 파일을 삭제했습니다.
